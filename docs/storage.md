# Local storage

The app keeps one SQLite database on the device, through
[drift](https://drift.simonbinder.eu). It holds what has to survive an app
kill or a missing network: unsent games, the cached library and analyses, the
ids of running analysis jobs, the two outboxes, and a few flags. The GraphQL
cache is not in here; it stays in memory.

Everything lives in `lib/core/storage/`:

    app_database.dart        AppDatabase: tables, DAOs, schema version, migrations, wipe
    tables/*.dart            one file per table
    daos/*.dart              one DAO per table; the only place with queries
    converters.dart          DateOnlyConverter (calendar dates as YYYY-MM-DD)
    *.g.dart                 generated by tool/gen.sh, committed

Features import `package:bogner_chess/core/storage/app_database.dart`, which
exports the tables, row classes, enums and DAOs. Features call DAO methods.
They do not write drift queries of their own: a query that a feature needs and
that is missing belongs into the DAO, with a test.

## Opening it

    final db = AppDatabase.open();                  // the app
    final db = AppDatabase(NativeDatabase.memory()); // a test

`AppDatabase.open()` uses `drift_flutter`: the file is `bogner_chess.sqlite`
in the application support directory (backed up by iOS, invisible in the Files
app), and queries run in a background isolate. Open it **once** per process
and close it never, or on tear-down in tests. Both constructors take an
optional `clock`; every DAO takes its "now" from `db.now()`, so a test controls
time by passing a fake.

SQLite itself comes with the `sqlite3` package (version 3), which uses a Dart
build hook: `flutter build`, `flutter run` and `flutter test` download a
prebuilt SQLite for the target platform from the package's GitHub release,
check it against a sha256 that is part of the package on pub.dev, and bundle
it. On iOS that is `Frameworks/sqlite3.framework` inside `Runner.app`; there
is no CocoaPods or Swift package involved, and nothing to
install on a developer machine or on CI (neither `libsqlite3-dev` nor
anything else). The first build after `flutter clean` needs network access to
github.com. `sqlite3_flutter_libs` still shows up in `pubspec.lock` as
`0.6.0+eol`, because `drift_flutter` depends on it; that version is an empty
package.

## Rules of the schema

- **Owner scoping.** Every row that belongs to an account carries
  `owner_sub`, the `sub` claim of the token. Every DAO method takes the owner
  as its first argument and puts it into the `WHERE` clause, for reads and for
  writes. The storage layer has no notion of a current user, so a query
  without an owner cannot be written by accident. The exceptions are
  `event_outbox` (a device-level queue; `owner_sub` is nullable because events
  exist before sign-in) and the app-level keys of `kv`.
- **Timestamps** are drift `dateTime()` columns in the default mode: unix
  seconds in an INTEGER column. Sub-second precision is dropped, and a value
  read back is a local-time `DateTime`. Compare instants
  (`isAtSameMomentAs`, `isBefore`), not fields. Every ordered query has a
  tie-breaker after the timestamp.
- **Calendar dates** (`cached_games.played_date`) are TEXT `YYYY-MM-DD`
  through `DateOnlyConverter`. A date of play has no time zone.
- **Enums** are stored by name (`textEnum`). Reordering values is free;
  renaming or removing one is a migration.
- **JSON columns** (`meta_json`, `summary_json`, `payload`, `props_json`) are
  opaque text to this layer. The feature that writes them owns the format.
  `drafts.meta_json` belongs to `DraftMeta`
  (`lib/features/submit_queue/domain/draft_meta.dart`): the keys of
  `GameMetadata.toJson` at the top level, plus a `draft` object with what only
  the device cares about (`source`, `cursorPly`, `orientation`,
  `analysisHold`). Reading it never throws; unknown or damaged content reads
  as "not known". That is why the submit queue needed no schema change.
- **Upserts never cross owners.** `cached_games`, `cached_analyses` and
  `pending_jobs` have the server id as the primary key. An upsert for owner A
  on an id that is stored for owner B is ignored.

## Tables

| Table | Key | What |
| --- | --- | --- |
| `drafts` | `id` (uuid); `client_game_id` unique | Games entered on the device, with the submit-queue fields (`state`, `attempts`, `last_error`, `next_attempt_at`, `server_game_id`). |
| `cached_games` | `game_id` | The library list as last fetched: `summary_json` plus the columns the list sorts and filters by (`played_date`, `opponent_name`, `opponent_search`, `updated_at`), and `fetched_at`. |
| `cached_analyses` | `game_id` | The analysis document as raw JSON with `schema_version`, `schema_minor`, `fetched_at`. |
| `pending_jobs` | `job_id` | Analysis jobs the poller watches: `game_id`, `state`, `created_at`, `last_polled_at`. |
| `event_outbox` | `id` autoincrement | Analytics events: `owner_sub` (nullable), `device_id`, `session_id`, `name`, `occurred_at`, `props_json`, `attempts`. Capped at 1000 rows, oldest dropped first. |
| `feedback_outbox` | `id` autoincrement; (`owner_sub`, `comment_id`) unique | Thumbs on coach comments: `rating` up, down or cleared. Latest wins per comment. |
| `kv` | `key` | String flags. `KvDao` prefixes keys: `app/<key>` or `owner/<len>/<sub>/<key>`. |

`cached_games.opponent_search` is `opponent_name` in lower case, written by
the DAO with Dart's Unicode-aware `toLowerCase()`. SQLite's `LIKE` and
`lower()` fold case for ASCII only, which would not find "Müller" for
"müller".

The draft state machine is documented on `DraftsDao`. In short: `editing`
(autosave works only here) → `ready` → `submitting` → `submitted`; a failed
attempt goes back to `ready` with `next_attempt_at` set, or to `failed` when
the queue gives up; `retry` and `reopen` lead out of `failed`. Every
transition is a guarded `UPDATE ... WHERE state IN (...)` and returns whether
it happened, so two racing callers cannot both win. The back-off *policy*
(how long, how many attempts) belongs to the submit queue; the DAO only stores
its result.

## Sign-out and account deletion

- `db.wipeOwner(sub)` removes every row of that account in one transaction,
  including its `kv` keys and its analytics events. `keepDrafts: true` leaves
  the drafts, for a sign-out the user did not choose (expired session).
- `db.wipeAll()` empties every table.

Neither deletes the database file, so open streams keep working and emit the
empty state.

## Changing the schema

The schema is versioned from the first release on. For every version there is
a frozen description of it, `drift_schemas/drift_schema_v<N>.json`, and
`test/core/storage/migration_test.dart` checks two things against those files:

1. A fresh install of the current code has exactly the schema of the newest
   dump. **This fails as soon as a table changes without a new version**,
   which is the mistake that otherwise only shows up on users' devices.
2. For every pair of versions, opening an old database with the current code
   migrates it to exactly the schema of the newer dump.

To add a column, a table or an index:

1. Change the table class in `lib/core/storage/tables/`. A new column on an
   existing table must be nullable or have a default (`withDefault`), or the
   `ALTER TABLE` fails on a table that has rows.
2. Raise `schemaVersion` in `app_database.dart` by one.
3. Regenerate code, dump the new version, and regenerate the helpers:

       tool/gen.sh
       dart run drift_dev schema dump lib/core/storage/app_database.dart drift_schemas/
       dart run drift_dev schema steps drift_schemas/ lib/core/storage/generated/schema_versions.dart
       dart run drift_dev schema generate drift_schemas/ test/core/storage/generated/

   The dump command writes `drift_schema_v<new>.json` and leaves the older
   files alone. **Never edit or re-dump an old version**: it describes what is
   on users' devices. Both output directories are called `generated/`, which
   exempts them from the format, header and analyzer checks.
4. Write the migration in `AppDatabase.migration`. With the generated steps
   file it looks like this (the first time, replace the `onUpgrade` that
   throws and add
   `import 'generated/schema_versions.dart';`):

       onUpgrade: stepByStep(
         from1To2: (m, schema) async {
           await m.addColumn(schema.drafts, schema.drafts.source);
         },
       ),

   Use the `schema` argument, not `drafts` of the live database: `schema` is
   the snapshot of version 2, and the step must still mean the same when
   version 5 exists. `m.createTable`, `m.createIndex`, `m.alterTable(TableMigration(...))`
   (for anything SQLite cannot do with `ALTER TABLE`: changing a type, a
   constraint, dropping a column with an index) are the other tools.
5. Run `flutter test test/core/storage`. The migration test now has a
   `from 1 to 2` case without any edit. If the migration moves or rewrites
   data, add a data test next to it: `verifier.schemaAt(1)`, insert rows
   through `schema.rawDatabase` or the generated `v1` classes, migrate, read
   with `AppDatabase`. See the drift documentation, "Verifying data
   integrity".
6. Update the table list above and commit everything together: tables,
   `*.g.dart`, the new JSON, both `generated/` directories, the migration and
   its tests.

Do not use `dart run drift_dev make-migrations`. It does the same three
things, but writes the steps file as `lib/core/storage/app_database.steps.dart`
and its tests to a directory of its own choice; a generated file outside a
`generated/` directory fails the header check.

Downgrades are not supported; drift refuses to open a database with a higher
version than the code knows. That matters for TestFlight: a build with schema
version N+1 that was installed once makes the device unusable for a build
with version N until the app is deleted.

## Testing

`test/core/storage/test_database.dart` has `openTestDatabase(FakeClock)` and
the two owners `alice` and `bob`. Every DAO test file ends with an "owner
scoping" test: whatever is added to a DAO, add the line that shows that owner
A cannot read or change the row of owner B. Tests of features that need a
database use the same helper; an in-memory database is created in well under
a millisecond, there is no reason to mock a DAO.

Streams: `await dao.watchX(...).first` reads the current value;
to observe several emissions, listen, `await pumpEventQueue()` between the
writes, and cancel.
